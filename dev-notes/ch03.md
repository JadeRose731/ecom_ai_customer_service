## 翻车与返工:Milvus 2.6 单容器 embedded etcd 会 panic(已按推荐项返工)

- **现象**:首版按「单容器 `ETCD_USE_EMBED=true` + `COMMON_STORAGETYPE=local`」起容器,反复重启,`docker logs` 报 `panic: embedded etcd can not be used under distributed mode`,容器永不 healthy,测试连 19530 全挂。
- **定位**:Milvus **2.6 起官方移除了 embedded etcd**,单容器嵌入式形态在 2.6 不再受支持(官方 issue #43760 / discussion #45420 同款报错);官方 compose 自 2.6 起改为**三容器**:etcd(元数据)+ MinIO(对象存储)+ standalone,消息队列用内嵌 Woodpecker(以 MinIO 为 WAL 后端),无需额外容器。
- **处理(推荐项,已记录)**:docker-compose.yml 推倒重写为**官方三容器配方**(镜像与官方文件逐一对应:etcd v3.5.25 / minio RELEASE.2024-05-28T17-19-04Z / milvus v2.6.0;`ETCD_ENDPOINTS=etcd:2379`、`MINIO_ADDRESS=minio:9000`)。两处刻意偏差:① minio 不映射宿主 9000/9001 端口(应用只走 19530,避免宿主端口冲突);② 数据卷目录沿用项目 `data/volumes/` 惯例。清掉 panic 残留数据卷后重启。
- **教训**:「standalone」不等于「单容器」;跟着官方 compose 配方走,别手拼 embedded etcd 环境变量。
- **返工续**:换官方三容器后仍起不来,`panic: failed to create etcd client: context deadline exceeded`——官方文件里 `ETCD_ENDPOINTS=etcd:2379` 里的 `etcd:` 是**它的服务名**;我把服务改名 `milvus-etcd` 后忘了同步 endpoints,compose 网络里没有叫 `etcd` 的主机,DNS 等到超时。改 `ETCD_ENDPOINTS=milvus-etcd:2379`、`MINIO_ADDRESS=milvus-minio:9000` 并 `depends_on: condition: service_healthy` 后正常。(另:grep 日志时注意 2.6 的 aws sdk init 行自带 `log level:fatal`,别误判成 panic。)
- **测试适配(可见性延迟)**:Standalone 默认 Bounded 一致性,upsert 成功后立查 count/search 有 ~1s 延迟(Lite 是即时的);测试里 upsert 后 `client.flush(collection)` 落盘即立即可见。生产无此问题(向量化离线写、检索在线读,不同时点)。
- **影响范围**:单测里「临时 Milvus Lite 文件」改为「Docker Standalone + 测试夹具逐用例 drop/重建集合」(测试库与 MySQL 测试同款依赖 Docker);ch04 本就要升级 Milvus Standalone 做混合检索,此改动让 ch03 直落 ch04 目标形态,后续零迁移。
